Act 01 · Relatable moment

Did you ever embed something native?

You build a beautiful Flutter checkout screen. Then the payment provider says: “Use our Android SDK” or “Open this WebView.” Suddenly, your all-Flutter screen contains a guest from another UI world.

The key term

Platform View

A Platform View is a native platform UI component hosted inside a Flutter app. On Android, the actual view is an Android View; Flutter provides the embedding mechanism and layout integration.

Example: Flutter's WebView widget is the Flutter-facing API. The web content is displayed by an actual native Android WebView.

Act 02 · The aha moment

Two different worlds. One display.

The issue is not that Flutter cannot show native UI. It can. The interesting engineering problem is how the output of different UI systems is coordinated into one frame.

Know these terms: Widgets describe UI; Elements connect widget configurations to live instances; RenderObjects handle layout, hit testing and painting; the engine rasterizes the resulting scene.

Technical nuanceThe framework does not independently paint each widget into its own bitmap. It builds a rendering structure/scene which the engine processes.

The display has a refresh schedule. Miss the presentation deadline and a frame may arrive late, producing visible stutter or a repeated frame.

Aha: The problem is not “Flutter cannot display Android UI.” The problem is “How should Flutter and Android combine their visual output while preserving native behavior, correct layering, synchronization, and acceptable performance?”

Don't blame composition for everything

Overlay appears behind native view

Investigate surface/layer ordering and the selected composition strategy.

Keyboard doesn't resize screen

Investigate focus, IME, window insets, and soft-input configuration. Not automatically an HCPP problem.

Gesture behaves strangely

Investigate Flutter hit testing, gesture recognizers, and native input handling.

Animation stutters

Investigate frame workload, UI/raster threads, native work, GPU and synchronization.

Act 03 · The solution moment

Three ways to merge the worlds

Think of these as different answers to the same question: how does the native view's output become part of the Flutter app's final screen?

Texture Layer Hybrid Composition

Turn native output into a texture Flutter can use

Kid version: Android draws its part, makes it available as a texture, and Flutter places that texture into its own picture.
Native
Android View→Texture
Flutter
Flutter scene + texture→Flutter composition
Why it's useful

Flutter retains more control over composition. Common transforms and effects can integrate naturally.

Trade-offs

Some native surface-backed behavior and certain accessibility/text magnification cases can be constrained; workload-specific jank can occur.

Pro-level nuanceA texture is a GPU-accessible image resource. Do not describe this as merely taking a screenshot of the native view.
Traditional Hybrid Composition

Let Android keep its native view

Kid version: Don't turn the native view into a Flutter texture. Let Android keep the native view, then arrange Flutter's content around it.
Flutter
Flutter background layerFlutter overlay layer
Android
Native Android View in View hierarchy
Android view hierarchy composes the relevant layers

Flutter content is rendered into ImageReader-backed FlutterImageView layers, including background/overlay arrangements around the native view.

Why it helped

Native view behavior and fidelity are preserved; surface-backed views are better supported.

The cost

Traditional HC can require expensive synchronization/coordination between Flutter raster work and Android platform-thread work.

Say it accurately“HC can introduce thread-coordination overhead that affects Flutter frame performance.” Avoid saying HC is always slow or always causes jank.
Hybrid Composition++

Use Android's native surface synchronization

Kid version: Both artists keep their own proper drawing surfaces. Android has a system-level way to coordinate those surfaces so they can be presented together.
Flutter
Impeller + Vulkan→Flutter Surface
Android
Native Platform View→Native Surface
↓ Surface transaction synchronization ↓
SurfaceFlinger → final display composition

HCPP aims to reduce the synchronization overhead associated with traditional Hybrid Composition by using Android's native surface transaction mechanisms.

ImportantIt is an engine/platform composition strategy, not a widget and not a universal performance switch.

Compare the approaches at a glance

StrategyMental modelStrengthTrade-off / constraint

HCNative view stays nativeNative fidelity and surface behaviorThread/synchronization coordination cost
HCPPNative surfaces coordinated by AndroidAims to reduce HC synchronization overheadSpecific Android, Vulkan, and Impeller requirements

Virtual Display is another historical/legacy strategy worth recognizing, but it does not need to dominate this talk. Keep your core comparison focused on TLHC, HC, and HCPP.

The deep dive · Become fluent

HCPP, without the hand-waving

Now that you understand the problem and the earlier trade-offs, the HCPP architecture should feel logical rather than magical.

Simplified HCPP composition model
Flutter side
Flutter framework→Impeller / Vulkan→Flutter surface
Native side
Android Platform View→Native surface
Coordination
SurfaceControl / transaction synchronization
Display
SurfaceFlinger→One presented screen

Surface

A place where a producer can provide image buffers for display.

Think of it as a stream of frames made available to the Android graphics system. Flutter and native components can produce their own visual output.

SurfaceControl

A remote control for a surface and its properties.

Android API used to control surface layers and apply transactions. Transactions can group surface-state updates so they are coordinated.

Surface transaction

A coordinated set of changes, rather than unrelated changes at random times.

It is part of Android's surface-control mechanism. The talk-level idea is synchronization of surface state/presentation.

SurfaceFlinger

Android's system display compositor — the final stage that combines display layers.

It is not Flutter's renderer. It composes eligible surfaces/layers for the display.

The important architectural shift: HCPP lets Flutter content and native platform content use native surfaces, then relies on Android's transaction/surface composition mechanisms to coordinate them. The goal is to avoid the traditional HC synchronization bottleneck.

Why Impeller and Vulkan?

Impeller

Flutter's rendering engine. It is responsible for rendering Flutter's scene using a graphics backend.

Vulkan

A low-level graphics API. HCPP's documented Android path requires Impeller using the Vulkan backend on a capable device.

Requirements and caveats checklist

If requirements are not met, Flutter may use the existing configured Platform View strategy. Exact behavior, defaults, flags, and support status are version-sensitive. Verify against the official docs and the Flutter SDK you will use on stage.

Can you toggle HCPP with a button?

No — not as a normal runtime Dart toggle. HCPP is a global engine/platform-view configuration selected when the Flutter engine/app starts. It is not a property that a widget can flip while the same engine is running.

For a reliable conference demo: prepare two prebuilt variants — HC baseline and HCPP — using the same app and workload. Install both beforehand, switch apps, and reconnect DevTools to the active process.

Verify that the baseline really uses traditional Hybrid Composition, not TLHC. Also verify the exact enable/disable configuration against your Flutter SDK; do not assume omitted metadata disables HCPP across versions.

Act 04 · The demo lab

Turn the architecture into evidence

Your demo is not “look, this one feels faster.” It is a controlled experiment: same device, same Flutter UI, same native view, same workload — different composition strategy.

Build the test app

  • Flutter animation / updating panel
  • Real native Android WebView
  • Repeatable scrolling workload
  • Reset and start controls
  • Visible HC / HCPP build label

Keep the experiment fair

  • Same physical Android device
  • Same content and interaction sequence
  • Same refresh-rate conditions
  • Repeat runs; note thermal state
  • No network dependency on stage

DevTools shows Flutter frame pipeline activity. It does not fully expose Android SurfaceFlinger composition or every native surface transaction.

UI thread

Flutter framework/Dart work: build, layout, paint/layer-tree production and related framework activity. Expensive work can delay producing a frame.

Raster thread

Flutter engine rendering work: processes the scene and performs graphics work. Expensive rendering can delay frame completion.

Profile mode, not debug mode

flutter run --profile

Profile mode is intended for performance analysis with tracing support and behavior closer to release than debug. Use a physical device; emulator results are not representative for this comparison, and profile mode is not supported on emulators/simulators for this purpose.

Stage-ready checklist

Be honest with the result. Do not promise a fixed percentage improvement. If the difference is small, that is still useful: it tells you something about this device and workload. HCPP changes the composition architecture; measure whether it helps your actual case.
Act 05 · Closing

What should an engineer walk away with?

1. Platform Views are a boundary.

A native view inside Flutter is not just another Flutter-painted widget.

2. Composition strategies make trade-offs.

TLHC, HC and HCPP solve the same broad problem using different rendering/composition paths.

3. Performance must be measured.

Choose based on native behavior, device support, actual workload and traces — not hype.

A closing line worth rehearsing

“The next time you drop a native view into Flutter, don't just ask, ‘How do I embed it?’ Ask, ‘How will these two worlds agree on the final frame?’”

Claims to avoid on stage

“HCPP is always faster.”Performance depends on workload, device and implementation.
“HC always causes jank.”It can introduce overhead; it is not universally slow.
“All native views use SurfaceView.”Android View and SurfaceView are different concepts.
“Flutter and Android have separate GPUs.”Different UI/rendering paths ultimately use the Android graphics/display system.
“DevTools proves SurfaceFlinger is faster.”Flutter DevTools is not a full system compositor trace.
“A Dart button toggles HCPP.”It is an engine/platform configuration, not a widget runtime property.

What is a Platform View?
A real native platform UI view hosted inside Flutter. On Android, the underlying object is an Android View.
What is composition?
Combining visual output from Flutter and native Android paths into the final screen, with correct ordering and timing.
What is TLHC's mental model?
Native view output is made available through a texture-backed path that Flutter can compose into its scene.
What is the HC trade-off?
Native fidelity and behavior, with potential synchronization/thread coordination overhead.
What is HCPP's key idea?
Use native surfaces and Android transaction synchronization to coordinate Flutter and native content, aiming to reduce traditional HC overhead.
